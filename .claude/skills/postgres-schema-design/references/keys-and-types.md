# Keys and types

The two decisions that are hardest to reverse once there is data.

---

## Natural or surrogate

They answer different questions, and the mature position is usually **both**: a
surrogate for children to reference, and a `UNIQUE` on the natural key so the
database still knows what makes two rows the same row.

```sql
CREATE TABLE racks (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- stable handle
  gateway_id TEXT NOT NULL,
  rack_id    TEXT NOT NULL,
  UNIQUE (gateway_id, rack_id)                                  -- the real identity
);
```

**Use a natural composite key as the primary key when** it is the physical
address of the thing, it never changes, and children reference the whole address
anyway:

```sql
PRIMARY KEY (gateway_id, rack_id, slot_number, channel_id)
```

For current-state tables this is right. The key *is* the address, a surrogate
would add nothing, and `ON CONFLICT` on exactly that key is what makes a
redelivered message idempotent.

**Use a surrogate when** the natural key can change (an email, a username, a
document number), or when it is wide and would be copied into many children.

**The cost of a natural key** is that a change to it has to propagate. `ON UPDATE
CASCADE` exists for this, but a cascading update of a key that appears in five
child tables is a large write under lock. If the value can change, it is not a
key, it is an attribute with a unique index.

### The unused surrogate

Worth noticing in an audit: a table with `id BIGSERIAL PRIMARY KEY` plus
`UNIQUE (a, b)` where nothing in the codebase ever references `id`. That is an
extra index maintained on every insert for nothing. Either make `(a, b)` the
primary key, or leave it and know why.

## Generating surrogate keys

```sql
-- Preferred. SQL-standard, cannot be overwritten by accident, no sequence
-- ownership surprises on table copy.
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- Legacy. Still everywhere, still works. Creates a sequence you own separately,
-- and lets a client write the column directly (so a client can desynchronise it).
id BIGSERIAL PRIMARY KEY
```

`GENERATED BY DEFAULT AS IDENTITY` is the middle ground when a data loader needs
to supply ids.

### UUIDs

| Choice | When |
| --- | --- |
| `bigint` identity | the default; smallest, fastest, index-friendly |
| UUIDv7 (`uuidv7()` in PG 18, or generate in the app) | id must be created before the row, or by a client, and must still be time-ordered |
| UUIDv4 | id must be unguessable, and you accept the index cost |

The thing to know about v4 as a primary key: it is random, so inserts scatter
across the btree instead of appending to the rightmost page. That means more page
splits, worse cache locality and a bigger index. UUIDv7 is time-prefixed and
inserts like a sequence while keeping client-side generation. If you need UUIDs,
need v7.

**The pattern worth copying** — a surrogate for ordering, a UUID for reference:

```sql
CREATE TABLE predictions (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  prediction_id UUID NOT NULL UNIQUE,   -- what children reference
  ...
);
CREATE TABLE fault_risks (
  prediction_id UUID NOT NULL REFERENCES predictions (prediction_id) ON DELETE CASCADE
);
```

The producer mints the UUID before the parent row exists, so parent and children
can be written without a round trip in between, while `id` still gives cheap
ordering and pagination.

### Application-generated text ids

`id TEXT PRIMARY KEY` filled by the application is a legitimate choice — it keeps
id minting out of the database and makes client-side optimistic creation easy. Two
things to add when you do it:

```sql
CHECK (id <> '' AND length(id) <= 64)
```

Without them the column accepts the empty string and a megabyte of text.

## Types, in the order people get them wrong

### Time

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

`timestamptz` always. `timestamp` (without time zone) stores a wall-clock reading
with no idea which wall, and the bug appears once, in another time zone, in
production. `timestamptz` is the same 8 bytes.

- `now()` / `CURRENT_TIMESTAMP` — transaction start time. What you almost always
  want, and stable within a transaction.
- `clock_timestamp()` — actual current time, for measuring a duration inside one
  transaction.
- For a microsecond epoch from a device, `BIGINT` is correct and sufficient:
  microseconds fit in a signed 64-bit integer until the year 294247. `NUMERIC`
  for the same value costs space and comparison speed for nothing.
- For a duration, `interval` beats an integer plus a naming convention.
- For a validity period, one `tstzrange` column beats `valid_from` + `valid_to`,
  because it can carry an exclusion constraint.

### Numbers

| Use | Type |
| --- | --- |
| money, anything that must add up exactly | `NUMERIC(12,2)`, or `BIGINT` of minor units |
| a sensor reading, a score, a ratio | `DOUBLE PRECISION` |
| a count | `INT`, or `BIGINT` if it could pass 2.1 billion |
| a percentage | `INT` or `NUMERIC(5,2)` with `CHECK (… BETWEEN 0 AND 100)` |

`DOUBLE PRECISION` for money is the classic defect: `0.1 + 0.2 <> 0.3`, and the
error compounds over a ledger. `NUMERIC` without precision is arbitrary-precision
and fine; `NUMERIC(12,2)` also documents the intent.

### Text

`TEXT` everywhere. In Postgres `varchar(n)` is `text` with a length `CHECK`, and
carries no performance benefit — it only makes "the limit changed" a table
alteration. If you want a bound, say so:

```sql
name TEXT NOT NULL CHECK (length(name) <= 200)
```

`char(n)` is space-padded and a trap. Never.

For case-insensitive comparison, in order of preference:

1. a non-deterministic collation (`CREATE COLLATION … (provider = icu, locale =
   'und-u-ks-level2', deterministic = false)`) — correct, and the modern answer;
2. a stored lowercased column with `CHECK (col_lc = lower(col))` — explicit,
   indexable, works everywhere, and what most codebases end up with;
3. a unique expression index on `lower(col)` — no extra column, but every query
   must remember to write `lower()`;
4. `citext` — convenient, an extension, and its semantics surprise people around
   `LIKE` and locale.

### Specialised types that earn their place

| Type | Instead of | Why |
| --- | --- | --- |
| `inet` / `cidr` | `TEXT` for an IP | validates on write, supports `<<=` containment, sorts numerically |
| `jsonb` | `json`, `TEXT` | binary, indexable, deduplicated keys; `json` only preserves byte-exact input |
| `tstzrange` | two timestamp columns | one value, `&&` overlap, exclusion constraints |
| `ltree` | a materialised path in `TEXT` | ancestor/descendant operators and a GiST index |
| `bytea` | base64 in `TEXT` | 33% smaller, no encode/decode |
| `enum` arrays / `TEXT[]` | a join table | only when elements are never queried individually |

`inet` is the one most often skipped. The trade-off to weigh honestly: converting
an existing `TEXT` ip column rewrites the table and every reader that does string
comparison. On a new column, use `inet`. On an existing one, a `CHECK` that it
parses is the cheap 80%:

```sql
CHECK (ip = '' OR ip ~ '^[0-9a-fA-F:.]+(/[0-9]{1,3})?$')
```

### Port numbers, and other numbers stored as text

```sql
port TEXT    -- accepts 'banana'
port INT CHECK (port BETWEEN 1 AND 65535)
```

If a column holds a number, make it a number. The usual reason it is `TEXT` is
that a form posts a string; that is the form's problem, not the table's.

## Column order

Not correctness, but free: Postgres aligns fixed-width types, so declaring
fixed-width columns before variable-width ones reduces padding. On a wide table
with many rows it is a measurable storage difference. Never worth a migration on
its own; worth getting right in a new table.
